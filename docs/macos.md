# Native Apple Silicon build

The macOS target executes prepared ARM64 game code with a direct Metal 4 renderer. It supports preparation for 1.4.3 (default) and 1.2.1. It requires Apple Silicon, macOS 26+, Xcode with its Metal toolchain, Python 3.14+, Ninja and .NET 10 for building the shader service. The packaged game needs neither Python nor .NET.

Full-game compatibility and 3840x2160 at 144 rendered frames per second are acceptance targets. A successful build or synthetic probe does not establish gameplay performance, physics correctness or driver stability. The pinned upstream renderer has previously recorded driver faults during full-game submission; game-data runs on the target Mac must resolve that boundary before declaring the port ready.

## Build

Install the tools and dependencies, then create the Python environment:

```sh
brew install ninja opus libvpx llvm dotnet openssl@3 brotli uv
uv venv --python 3.14 .venv-py314
uv pip install --python .venv-py314/bin/python -r tools/requirements-macos.txt
tools/fetch_refs.sh
```

Install Xcode's Metal Toolchain if `xcrun --find metal` fails. Static libraries must contain ARM64 and target macOS 26 or earlier. The builder checks their deployment targets and uses an installed compatible keg when the newest Homebrew bottle targets a newer OS.

Copy `config.macos.example.toml` to the ignored `config.local.toml`. Set paths to the base game, cumulative update, key file and firmware directory. Keys are passed by path. The native host requires verified system shared fonts, including for availability queries. Extraction and prepared game files stay under `build/` and `generated/`.

For a combined NSP, use the same path for `input.base` and its entry in `input.updates`. The importer selects the base and BKTR update independently and checks the resulting modules and RomFS against the supported version hashes. If the container omits its ticket, set `input.title_keys` to the matching encrypted `title.keys` or `title.keys_autogenerated` file. Title keys pass to hactool through stdin; normalized key files are never written.

```sh
.venv-py314/bin/python tools/build_game.py --target macos-arm64 --version v143 --extract --package
```

This extracts and verifies inputs, rewrites the ARM64 modules, runs structural/differential and native-call gates, creates runtime tables, prepares shaders and packages a locally signed app:

```text
build/macos-arm64/v143/TotK Recomp.app
```

When verified extraction already exists, use `--prepare-game --package` instead of `--extract --package`. Later builds can use `--package` alone. Use `--version v121` for 1.2.1. The builder uses the same pinned sources for both versions. Its source checkout in `refs/` remains untouched; changes are applied to an ignored export.

The host uses `-O3`, ThinLTO with an incremental linker cache, and dead stripping. Diagnostic entry points and probe objects are excluded from the game build. Source exports preserve timestamps only for unchanged bytes, so editing one patch does not rebuild unrelated objects. Static-library and compiler changes invalidate their consumers.

Shader preparation deduplicates identical MSL and reuses atomically published metallibs under a compiler/toolchain identity. These assets live outside the replaceable source export. An unchanged shader does not start the Metal compiler again. Temporary Cryptex installation paths are excluded from the compiler identity, so remounting the same Metal toolchain does not invalidate its libraries. Offline and runtime compilation both target Metal 3.2 with safe arithmetic. Precise multiply/add helpers use local contraction controls so the compiler can inline them without fusing separately rounded operations.

The signature is ad hoc for local use. Public distribution/notarization is a separate signing process. The playable app contains the player's game data and stays local.

## Build without game files

```sh
.venv-py314/bin/python tools/build_macos.py --probes --package
PYTHONPATH=tools .venv-py314/bin/python -m macos.check
PYTHONPATH=tools .venv-py314/bin/python -m macos.shaders
.venv-py314/bin/python tests/macos_shader_test.py
.venv-py314/bin/python tests/macos_shader_math_test.py
.venv-py314/bin/python tests/macos_shader_cache_test.py
.venv-py314/bin/python tests/macos_save_test.py -v
.venv-py314/bin/python tests/macos_layout_test.py -v
.venv-py314/bin/python tests/macos_benchmark_test.py -v
.venv-py314/bin/python tests/macos_trace_test.py -v
.venv-py314/bin/python tests/macos_build_test.py -v
.venv-py314/bin/python tests/macos_thread_test.py
```

`TotK Recomp Diagnostics.app` contains the real compiled host and renderer with explicit empty game tables. It refuses game boot. `--selftest` checks native execution and Metal 4 capability. The GPU runner tests masked clears, depth/stencil, resource aliasing/lifetimes, uniform snapshots, bindings and render-stream behavior under Metal validation; each run keeps separate logs. `--probe-warm-pipelines` compiles and executes 128 distinct render/compute pipelines with the startup and in-play worker limits. The shader test uses a synthetic Maxwell kernel through the native translator, SPIRV-Cross and Apple's Metal compiler. It contains no game shader. The shader arithmetic test uses `glslangValidator` to generate precise SPIR-V operations and compares MSL 2.3 and 3.2 helpers on the GPU, including signed zero and separate-rounding controls. The attachment-ledger probe exercises all eight color targets plus depth and stencil.

The attachment-feedback probe reads pixels back after pending clears, barriers with intervening draws, storage aliases, nested texture views and MSAA copies. Writable images retain their original destination. The resolution test also compares both runtimes' allocation budgets against the RomFS heap generator, including diagnostic 4K runs.

The native call-window test and hardware probe can also run without game data:

```sh
.venv-py314/bin/python build/macos-arm64/source/games/totk/scripts/test_call_window.py
mkdir -p build/macos-arm64/source/games/totk/analysis
make -C build/macos-arm64/source/games/totk probe-call PY="$PWD/.venv-py314/bin/python"
```

The macOS CI job builds both version configurations and checks CPU calls, save failures, layout and presentation accounting. Physical GPU/display acceptance runs on the target Mac.

## Rendering and measurement

The default profile fixes scene and output to 3840x2160, requests 144 Hz presentation, bounds the present queue to two tickets and disables MetalFX scaling/interpolation and experimental invisible-draw skipping. Runtime scaling/graphics toggles are locked. Required shader/pipeline failures stop strict rendering. The clock uses `CLOCK_UPTIME_RAW` without the upstream 120 Hz minimum-step clamp or per-call initialization and gate counters. Shader arithmetic keeps separate rounding; the native translator excludes Windows patch 0008 because it changes a support-buffer ABI the Metal host does not implement.

The game drives its render loop, and a dedicated presentation thread drains its FIFO through Metal drawables with vsync. The native profile disables the additional display-link scheduling step, which can replace queued game frames. GPU completion and the bounded queue provide backpressure; queued frames are not coalesced and no frames are generated.

The resolution patches disable the game's dynamic scene multiplier, including 1.2.1's emergency reduction, while preserving each effect's downsample ratio. Original instructions are checked before any write. Scene validation applies to full-canvas composition; smaller inventory and effect targets do not establish the presented scene's dimensions. With local 1.2.1 modules, `python tests/macos_resolution_test.py` executes both size producers against Unicorn.

Frame execution and command replay use user-interactive QoS. They keep the system's normal scheduling policy: loading and guest-worker waits make their work unsuitable for a fixed real-time CPU budget. The policy probe checks both frame threads without requiring game files. See Apple's [CPU scheduling guidance for games](https://developer.apple.com/videos/play/tech-talks/110147/) for QoS propagation and the limits of fixed-priority work.

Guest yields first hand their virtual core to an eligible game thread. With no eligible peer, they use an ARM execution hint: Darwin's `sched_yield` can delay the caller behind unrelated host work. Yield without migration retains its core; yield-to-any also admits lower-priority peers. Actual waits still release the virtual core and block. The thread test checks empty yields, peer priorities, affinity changes during wake-up, timed sleeps and optional polling backoff under AddressSanitizer and UndefinedBehaviorSanitizer.

Repeated argument addresses, exact pool lookups and uniform snapshot lookups use validated caches. GPU probes compare cached results with the authoritative path, including invalidation and encoder changes. The idle GPU spin-kernel thread and speculative pipeline prediction default off. Prediction scans can compile thousands of states that no draw uses; recorded startup pipelines still warm normally, and new states compile on demand. `TOTK_GPU_KEEPALIVE`, `TOTK_PSO_PREDICT`, `TOTK_ARG_BIND_CACHE`, `TOTK_POOL_QUERY_CACHE` and `TOTK_USNAP_INDEX` remain explicit environment controls for profiling; a microbenchmark win does not establish a gameplay win.

`TOTK_NATIVE_4K144=0` enables upstream diagnostic behavior. Such a run cannot satisfy strict acceptance.

Recorded pipeline warm-up compiles independent Metal states in bounded batches, keeping manifest priority. Descriptors and shader variants remain owned by one thread. `TOTK_WARM_THREADS` controls both library and pipeline workers (default up to eight, capped at two during play). New pipelines still compile before the draw that needs them; missing draws are never used to hide compilation delays.

Capture actual drawable presentation timestamps by launching the app executable from a terminal:

```sh
TOTK_FRAME_TRACE="$PWD/build/gameplay.csv" \
  'build/macos-arm64/v143/TotK Recomp.app/Contents/MacOS/TotKRecomp'
PYTHONPATH=tools .venv-py314/bin/python -m macos.benchmark build/gameplay.csv \
  --start-ticket 1000 --end-ticket 11000 --output build/gameplay-result.json
```

Select the measured gameplay segment explicitly; the analyzer reports excluded frames. Keep cold-start/shader preparation and steady gameplay captures separate. A gameplay segment must last at least 60 seconds. Every frame must have its own verified scene/output/drawable dimensions, a unique game-frame ID and a consecutive presentation ticket. Unknown scene coverage, repeats and dropped tickets fail acceptance. Average presented FPS must reach 144 and p99 must fit 6.944444 ms; tolerance covers only CSV timestamp quantization and floating point precision, reported in nanoseconds.

An explicit `TOTK_INPUT_FILE` accepts read-only `flag pass_gpu N` (up to 120 frames), `flag draw_log N` and `flag uw_log N` captures without unlocking graphics settings. `TOTK_PASS_GPU_FILE` selects a TSV for per-pass GPU timestamps. Exclude those instrumented frames from performance acceptance; pass timing changes submission boundaries.

Presentation callbacks enqueue immutable records; a dedicated writer formats and buffers CSV. It flushes at least once per second while active, and normal window close drains the queue. An abrupt process failure may lose the tail. Queue overflow or I/O failure stops the capture instead of silently dropping records. With tracing disabled the present path does not capture frame metadata.

These timing and dimension checks still need visual acceptance at a physical 4K/144 display mode: fixed allocation dimensions alone do not prove viewport coverage or image fidelity. Check the same saves/routes for terrain, transparencies, shadows, UI, physics, cloth, input latency and audio. Dynamic resolution, frame generation and reused frames cannot count toward the target. No target result is inferred from GPU probes or from another machine.

Use View > Enter Full Screen (Control-Command-F) for fullscreen presentation. The diagnostic input stream accepts `fullscreen 0|1` through the same window transition. Windowed composition can discard submitted drawables; only actual presentation timestamps count.

Click the game picture to capture the mouse; the capture click performs no game action. Escape goes back and releases it. Switching applications, minimising, resizing, changing fullscreen mode or opening text entry also releases it. Click again to resume. Controls > Mouse Sensitivity and Invert Mouse Y persist between launches. Control-Command-M toggles capture.

The 1.2.1 normal camera consumes mouse displacement directly, without the analog stick's dead zone, speed limit or frame-time multiplier. It retains the game's collision correction and pitch limits. Targeting, aiming and quick menus retain their right-stick input path. A stopped normal camera releases mouse movement to the menu; each delta is consumed once. The mouse uses GameController device deltas where available and AppKit relative events otherwise. 1.4.3 currently uses the analog mouse path; its direct-camera and font-cache adapters need separate version validation.

Prompt labels come from the same bindings as input. Keyboard or mouse use selects PC glyphs; controller use selects Xbox, PlayStation, Switch or generic controller glyphs. Disconnecting the last controller returns to PC prompts. Physical controller assignments from `controls.txt` are reflected in the labels. Existing cached font glyphs refresh when the active device changes, and bitmap prompts use immutable, cached Metal variants. The controller reference diagram uses the same mapping. Font-cache replacement is currently validated for 1.2.1.

`TOTK_MOUSE_SENS` sets initial sensitivity (0 to 10, default 1; zero disables capture), and `TOTK_MOUSE_INVERT_Y=1` reverses vertical camera input. The diagnostic input stream accepts `capture 0|1`, `mouse <dx> <dy>` (positive Y is up), `mousebutton <0..4> <0|1>` and `prompts <0..4>` (keyboard, Xbox, PlayStation, Switch, generic). Mouse buttons are left, right, middle, back and forward. These commands are disabled unless `TOTK_INPUT_FILE` is explicitly configured.

`tests/macos_mouse_test.py` checks delta ownership, frame-rate independence, brief clicks and focus changes. `tests/macos_game_input_test.py` checks hook installation, camera direction and protected modes. `tests/macos_prompts_test.py` checks actual bindings, device families and atlas replacement, including allocation failures; `tests/macos_prompt_assets_test.py` checks archive bounds and isolated layout changes. The C checks use AddressSanitizer and UndefinedBehaviorSanitizer.

## Player files and saves

| Data | Location |
|---|---|
| Versioned profiles | `~/Library/Application Support/TotKRecomp/<version>/` |
| Shader cache | `~/Library/Caches/TotKRecomp/<version>/<toolchain-OS-GPU identity>/` |
| Logs | `~/Library/Logs/TotKRecomp/` |

Fixed `TOTK_SHADER_CACHE` development overrides also receive the toolchain/OS/GPU namespace. Changing translator settings requires rebuilding the native toolchain; alternate Python/DLL/debug translators cannot reuse its cache.

Only one local app instance can own the player profile. A save writes to `save-tx/work`. Commit snapshots it with APFS copy-on-write, calls `fsync` on the files, atomically exchanges the committed directory, flushes publication metadata and completes one checked `F_FULLFSYNC` drive barrier before returning success. This barrier also persists every preceding file sync on the device. Failures return to the game and retain working data. Last writable-mount unmount rolls back to the committed generation; dirty work is kept in a recovery directory. Read-only mounts cannot modify either generation. Clean restarts do not accumulate recovery copies.

RomFS streaming has a separate handle-lifetime lock. Save publication cannot block asset reads, and closing an overlay file waits for its readers before releasing the descriptor.

The previous committed generation and interrupted recovery work remain under the profile. Recovery copies are deliberate player data; they are never silently pruned. Fault-injection tests cover copy/flush/publication failures and process termination. They do not simulate physically removing power from the storage device.
